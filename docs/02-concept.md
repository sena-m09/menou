# コンセプトと設計原則

中心となる考え方は「完了は会話の性質ではなく、成果物の性質である」です。エージェントが何と言ったかではなく、記録された検証結果と今のコードの状態から、完了してよいかを決めます。

## 設計原則

1. **手順ではなく、完了時の状態を宣言する**
   途中の作業順序は縛らず、完了しようとした時点で満たすべき条件だけを定義します。エージェントの進め方の自由を残し、保守もしやすくするためです。
2. **判定はモデルの外側で、決定的に行う**
   完了の判定はフックから呼ばれるコマンドで行い、エージェントの発言や LLM の判断には頼りません。Codex のフックは LLM による判定（prompt 型）を実行しないため、両対応の前提でもあります。
3. **結果は「どの状態に対するものか」とセットで記録する**
   検証結果には、そのときのコードの状態を表すハッシュ（フィンガープリント）を必ず添えます。完了時に今のフィンガープリントと比べ、一致しなければ古い結果として扱います。
4. **結果を書くのは基盤だけ**
   エージェントは検証コマンドを実行するだけで、結果ファイルを直接書きません。記録を偽る経路を減らすためです。
5. **基盤はチェックの中身を知らない**
   基盤から見れば、どのチェックも「コマンドを実行して合否を返すもの」です。Lint もエージェントレビューも同じ約束事に従えば、基盤を変えずに追加できます。
6. **関係ない作業の邪魔をしない**
   セッション中にコードが変わっていなければゲートしません。チェックごとに対象のファイル範囲を持ち、範囲外の変更では要求しません。
7. **詰まったら人に渡す**
   ブロック回数に上限を設け、超えたら完了を許可して人に確認を促します。逃げ道を場当たり的に足すのではなく、最初から設計に含めます。
8. **「不合格」と「エラー」を区別する**
   コードの問題による失敗と、ツールやネットワークの異常は分けて扱います。存在しない問題をエージェントが直そうとして迷走するのを防ぐためです。

## 用語

| 用語 | 意味 |
| --- | --- |
| ゲート | 完了しようとしたときに条件を確認し、満たさなければ作業を続けさせる仕組み全体 |
| チェック | ゲートで確認する検証の単位。Lint、E2E、レビューなど |
| フィンガープリント | チェック定義と、対象範囲のファイル内容から計算したハッシュ |
| 有効な記録 | 記録されたフィンガープリントが、今のフィンガープリントと一致している記録 |
| inline 方式 | 完了時に基盤がその場でチェックを実行する方式 |
| evidence 方式 | エージェントが事前にチェックを実行し、完了時は記録だけを確認する方式 |
| ベースライン | セッション開始時のコードの状態。ここから変化がなければゲートしない |

## 参考にした考え方

- Anthropic「Effective harnesses for long-running agents」：機能ごとの `passes` フラグで完了を宣言的に管理する
- Mokhov, Mitchell, Peyton Jones「Build Systems à la Carte」：前回の入力のハッシュを記録し、変化がなければ再実行しない verifying traces
- Birgitta Böckeler「Harness engineering for coding agent users」：テストや静的解析のような計算的なセンサーでエージェントを制御する
