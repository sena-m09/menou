# フィンガープリントに含める範囲

- 日付：2026-11-06
- 状態：採用

## 背景

[03-architecture.md](../03-architecture.md) では、フィンガープリントを「チェック定義そのもの + paths に含まれるファイルの内容」から計算するとしていました。ただ、次の 4 つが決まっていませんでした。

- `hint` や `severity` のように、検証の中身に関わらないフィールドを変えたときにも、過去の結果を無効にするか
- チェック定義をハッシュするときに、キーの順序・空白・既定値をどう扱うか
- `.gitignore` の対象のファイルを含めるか
- E2E の記録データ（スナップショットなど）を含めるか

あわせて、チェックの実行中に paths の中のファイルが書き換わる場合の扱いも決まっていませんでした。スナップショットの更新や自動修正をするコマンドで起こります。

## 決定

- チェック定義からは `run`・`paths`・`timeout` だけを含める。`id`・`mode`・`severity`・`hint`・`needs` は含めない
- 既定値を補ったあとの値でオブジェクトを組み立て、`JSON.stringify` した文字列をハッシュする。`paths` の並びは書かれたとおりにする
- `timeout` は、`mode` に関わらず既定値を補った値で含める
- `.gitignore` の対象のファイルは含めない。E2E の記録データも特別には扱わず、追跡されていて paths に入っていれば含まれる
- チェックを実行する前と後でフィンガープリントが変わったら、エラーとして記録し、チェックが対象のファイルを書き換えたことを知らせる

含めるのは、変えると合否が変わりうるフィールドです。`run` と `paths` は検証の中身そのもので、`timeout` は短くすると通っていたチェックが時間切れで落ちることがあります。`severity`・`needs`・`mode` は、落ちたときの扱い、評価の順番、誰が実行するかを変えるだけです。`hint` は案内の文言です。`id` は記録を探すときに使うので、フィンガープリントには入れません。

キーの順序をコードで決めるので、`.menou.json` でキーを並べ替えたり空白を変えたりしても、フィンガープリントは変わりません。

`.gitignore` の対象は `git add -A` が含めないので、それに任せます。含めると `node_modules` まで読むことになり、遅くなります。

実行の前後でフィンガープリントが変わったときに後の値で合格にすると、書き換えたあとの中身を誰も検証していないことになります。そのため、エラーにします。

## 影響

`hint` の言い回しを直したり、`mode` を inline から evidence に変えたりしても、E2E やレビューを取り直さずに済みます。

チェックが読むファイルでも、paths に入れていないものは、変えても記録が無効になりません。たとえば agent-review の `--rubric` で渡す観点のファイルは、paths に入れておかないと、観点を変えても前のレビュー結果がそのまま使われます。

`.env` や生成物のように、ignore されたファイルに頼るチェックは、そのファイルを変えても取り直されません。困る場面が出てきたら、含めるファイルを指定する方法を足します。

自動修正をするコマンド（`eslint --fix` など）は、チェックとしては使えなくなります。確かめるだけのコマンドを書いてもらうことになります。

`.menou.json` のスキーマにフィールドを足すときは、フィンガープリントに含めるかを決めます。決め忘れは、すべてのフィールドがどちらかに分類されているかを確かめるテストで見つけます。既定値を変えると、そのフィールドを省いていたチェックの記録が一度だけ無効になります。
