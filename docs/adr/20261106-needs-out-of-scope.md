# needs の前提のチェックが対象外なら、前提を満たしたとみなす

- 日付：2026-11-06
- 状態：採用

## 背景

[03-architecture.md](../03-architecture.md) の判定フローでは、`paths` の範囲がセッションの開始時（ベースライン）から変わっていないチェックは対象外になります。また、`needs` に書いた前提のチェックが通っていないチェックは、実行も判定もしません。前提のチェックが対象外になったときに、それを「通った」とみなすかが決まっていませんでした。

たとえば、review が lint を `needs` に持ち、review の範囲は変わったが lint の範囲は変わっていない場合です。次の 2 つを比べました。

| | 対象外なら満たしたとみなす | 今のフィンガープリントで合格した記録を求める |
| --- | --- | --- |
| 例の場合 | lint を求めずに review を求める | lint を通すまで review に進めない |
| セッションの前から lint が落ちていたとき | review に進める | エージェントが触っていない範囲の lint を直すまで進めない |
| `needs` の役目 | 前提が通ってから重いチェックを回す、という順番だけを決める | 順番に加えて、前提の範囲が今も通ることを求める |

`needs` は、Lint が通ってから E2E やレビューを回すための順番の指定です。前提のチェックの範囲が変わっていなければ、待つ理由がありません。合格した記録を求めると、変えた範囲のチェックだけを求めるという menou の考え方とずれます。

## 決定

- `needs` に書いた前提のチェックが対象外なら、前提を満たしたとみなす
- 前提のチェックが対象内なら、これまでどおり、今のフィンガープリントで合格したときだけ前提を満たしたとみなす

## 影響

セッションの前から落ちていたチェックが前提にあっても、エージェントが触っていない範囲なら、後ろのチェックに進めます。

前提のチェックについては範囲が変わっていないことだけを見るので、前提のチェックが今のコードで通るとは限りません。
