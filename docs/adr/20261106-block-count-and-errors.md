# ブロック回数の数え直しと、チェックがエラーになったときの扱い

- 日付：2026-11-06
- 状態：採用

## 背景

`maxBlocks` について、[04-config.md](../04-config.md) は「1 セッションで連続ブロックできる上限」、[05-agents.md](../05-agents.md) は「セッションごとのブロック回数を数え」と書いており、食い違っていました。いつ数え直すかで、上限に達するまでの長さが変わります。

[03-architecture.md](../03-architecture.md) は、チェックのエラー（終了コードが 0・1 以外）を「不合格と区別して記録し、続く場合は人に知らせる」としていました。エラーのときにブロックするか、何回続いたら人に知らせるかは決まっていませんでした。

[05-agents.md](../05-agents.md) で確かめた Claude Code の仕様は次のとおりです。

- Stop の入力の `prompt_id` は、ブロックして継続させている間は同じ値で、ユーザーが次に発言すると変わる
- `UserPromptSubmit` のフックは、ユーザーの発言のほかに、スケジュールしたタスクやサブエージェントの報告でも呼ばれる
- Stop のフックの出力のうち、利用者の画面に出せるのは JSON の `systemMessage`。stdout のプレーンテキストは画面にもコンテキストにも出ない
- Claude Code にも、ツールを呼ばずに 8 回続けてブロックすると完了させる上限がある

数え直すタイミングは、次の 3 つを比べました。

| | セッションの中で数え直さない | 新しい発言で数え直す | 新しい発言と、すべて満たしたときに数え直す |
| --- | --- | --- | --- |
| 長いセッションで依頼を重ねたとき | 前の依頼のブロックが残り、後の依頼ですぐ上限に達する | 依頼ごとに数える | 依頼ごとに数える |
| 1 つの依頼の中で、一度すべて満たしたあとにまた変更したとき | 前のブロックが残る | 前のブロックが残る | 数え直す |

エラーの扱いは、ブロックする案と、警告を出して通す案を比べました。通すと、コマンドが見つからない、タイムアウトした、のような設定や環境の誤りがあるだけで、ゲートが黙って効かなくなります。ブロックすると、ネットワークの異常のようにエージェントが直せないエラーでも、上限に達するまで続けることになります。

## 決定

- ブロック回数は、セッション ID ごとに数える。Stop の入力の `prompt_id` が前にブロックしたときと違えば数え直し、すべてのチェックを満たして通したときも数え直す
- ブロック回数が `maxBlocks` に達したあとの Stop では、不足があっても完了を許可し、人に知らせる。Claude Code では `systemMessage` で知らせる
- チェックがエラーになったときも、不合格と同じくブロックする。理由文では、コードの不合格ではなくチェック自体のエラーであることと、出力の場所を伝える
- エラーが続いた回数は別に数えない。人に知らせるのは、`maxBlocks` に達したときにまとめる
- ブロック回数は、ベースラインと同じく、worktree ごとの git ディレクトリの `menou/sessions/<セッション ID>/` に置く

## 影響

依頼ごとに `maxBlocks` 回までブロックするので、長いセッションでも後の依頼が前の依頼のブロックに引きずられません。

エラーで黙って通ることはなくなります。その代わり、エージェントが直せないエラーでは、`maxBlocks` 回ブロックしてから人に渡ります。理由文でエラーであることを伝え、存在しない問題をエージェントがコードで直そうとしないようにします。

`maxBlocks` を 8 より大きくしても、エージェントがツールを呼ばずに完了しようとし続けると、Claude Code の上限で先に完了します。

Codex に `prompt_id` にあたる入力があるかは、まだ確かめていません。M3 で確かめ、ない場合は、すべて満たしたときだけ数え直すことになります。
